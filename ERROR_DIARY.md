## 2026-11-17 — Мок не проверяет SQL в PostgreSQL

Поддельный курсор проверяет только Python-вызов: какие аргументы переданы в `execute`, как обрабатывается `rowcount`, закрывается ли курсор. Он не отправляет SQL в базу и не выявляет ошибки в синтаксисе запроса, названиях таблиц или ограничениях схемы.

Для проверки SQL нужен настоящий PostgreSQL. Для `delete_product` проверять:

- `delete_product(conn, 999)` возвращает `0` и не вызывает ошибку;
- временный товар, созданный в базе, удаляется с результатом `1`;
- `get_product_by_id(conn, product_id)` после удаления возвращает `None`.

Мок использовать только как дополнительную проверку передачи параметров и обработки результата, а не как замену интеграционному тесту с базой.

## Категория: запуск и окружение

### ModuleNotFoundError: No module named 'src' (повторялась 3+ раза)

- **Симптом:** `ModuleNotFoundError: No module named 'src'` при запуске скрипта из подпапки `scripts/`, который импортирует пакет проекта.
- **Причина:** скрипт запущен не из корня проекта (или не как модуль), поэтому корень не попадает в `sys.path`, и пакет `src` не находится.
- **Правило:** всегда `cd D:\python_course\SFMShop` и запускать `python -m scripts.<имя_без_расширения>`. Никогда не запускать файл «по пути» из другой директории.

### Изменения кода не подхватываются сервером

- **Симптом:** после правки эндпоинта в Swagger старое поведение / старый код.
- **Причина:** сервер запущен без автоперезагрузки.
- **Правило:** `uvicorn ... --reload` либо ручной перезапуск после каждого изменения.

### Файл создан не в той папке

- **Симптом:** скрипт лежит в `scripts\scripts\` вместо `scripts\`, запуск `python -m scripts.<имя>` его не находит, ментор не видит файл по пути из ТЗ.
- **Правило:** перед созданием файла сверять путь из ТЗ, после создания — проверять `python -m` запуском из корня.

## Категория: объекты и типы (самая частая)

### Сравнение объекта с числом вместо атрибута

- **Симптом:** `TypeError: '<' not supported between instances of 'Product' and 'int'` (и вариант `'Product' and 'Product'`).
- **Причина:** сравнивался объект целиком: `sorted_products[mid] < target_id` вместо `sorted_products[mid].id < target_id`; аналогично `sorted(products)` без `key` сравнивает объекты между собой.
- **Правило:** объекты самих себя сравнивать не умеют — сравниваем их атрибуты (`.id`, `.created_at`) либо передаём `key=` в `sorted()`. Проявление одного корня в трёх местах: сортировка каталога (24.11), бинарный поиск (24.11). Запомнить как единое правило, а не три случая.

### Печать объектов вместо атрибутов

- **Симптом:** в консоли `[<__main__.Product object at 0x000001FE...>, ...]` вместо данных.
- **Причина:** напечатан список объектов, а не их содержимое.
- **Правило:** `<... object at 0x...>` в выводе — сигнал: печатаешь не то. Цикл + f-строка с `product.id`, `product.name`, `product.price`.

### TypeError: 'function' object is not iterable

- **Симптом:** `TypeError: 'function' object is not iterable` в `sum(order_products_gen)`.
- **Причина:** передана сама функция, а не её вызов: пропущены скобки и аргументы.
- **Правило:** функция-генератор сама по себе — объект; чтобы получить значения, её надо **вызвать**: `sum(order_products_gen(orders))`.

### Аннотации: отсутствие и противоречие коду

- **Симптом:** фидбек ментора 24.11 «аннотации типов отсутствуют»; самостоятельно написал `-> None` у функции, которая возвращает товар.
- **Причина:** `None` как аннотация возврата означает «ничего не возвращает», а функция возвращала `product` или `None`.
- **Правило:** аннотация возврата должна совпадать со всеми ветками `return`. Варианты возврата — объединение: `-> Product | None` (современный синтаксис, Python 3.10+; раньше `Optional[Product]`).

### Присваивание лямбды в переменную

- **Симптом:** `key_products = lambda product: product.id`.
- **Причина:** стилистический антипаттерн (PEP 8: лямбду, которой хочется имя, оформляют через `def`); плюс type checker'ы хуже понимают такую запись.
- **Правило:** разовые лямбды пишутся строкой в месте использования: `sorted(products, key=lambda p: p.id)`.

## Категория: алгоритмы и данные

### Бинарный поиск по неотсортированному списку

- **Симптом:** (поймано до запуска) вызов `binary_search_by_id(products, i)` с исходным списком вместо отсортированного.
- **Причина:** бинарный поиск опирается на порядок; без него «больше/меньше» про произвольную половину ничего не значит — результат мусорный без ошибки.
- **Правило:** бинарный поиск — только по отсортированным данным, по тому же ключу, по которому сортировали.

### Функция обращается к внешней переменной вместо параметра

- **Симптом:** в теле `binary_search_by_id` использовалось имя `sorted_products` из вызывающего кода при наличии параметра.
- **Причина:** функция завязана на контекст вызова — в любом другом месте, где такой переменной нет, будет `NameError`.
- **Правило:** функция работает только со своими параметрами. Имена параметров и внешних переменных не обязаны совпадать — но ссылаться она должна на параметры.

### Замеры времени: один прогон и неправильный таймер

- **Симптом:** фидбек ментора 24.11: замеры не усредняются; `time.time()` вместо `time.perf_counter()`; в выводе встречалось `0.0000 сек`.
- **Причина:** одиночное измерение быстрой операции — шум, меньше разрешения таймера; `time.time()` — «настенные часы», могут дёргаться назад при синхронизации, грубое разрешение на Windows.
- **Правило:** для бенчмарков — только `time.perf_counter()` (монотонный, максимальное разрешение); измерять многократно (цикл из N прогонов) и усреднять или брать минимум; «прогреть» один вызов до замера.

### Ожидание, что данные «откуда-то берутся»

- **Симптом:** вопросы «откуда мы берём products?» при задачах на чистые алгоритмы.
- **Причина:** привычка к данным из БД/парсеров; в алгоритмических задачах данные генерируются синтетически циклом.
- **Правило:** если в ТЗ нет источника данных — генерируем сами (`for i in range(1000)`, `f"Товар-{i}"`, `timedelta`), это нормальный учебный приём.

## Категория: FastAPI и HTTP

### 422 Unprocessable Entity

- **Симптом:** запрос в Swagger падает с 422.
- **Причина:** тело запроса не соответствует Pydantic-модели: пропущено обязательное поле, неправильный тип, значение вне `Field(gt=0)` и т.п.
- **Правило:** 422 — это не «сломался сервер», а «данные не прошли валидацию модели». Читать раздел `detail` в ответе — там указано, какое поле и почему. Сверять тело запроса с моделью.

### Ложный успех: print + return вместо 404

- **Симптом:** (поймано на ревью) при «не найдено» код печатал в консоль и возвращался — клиент получал 201/200 с `null`.
- **Причина:** обработка ошибки не доходит до клиента.
- **Правило:** «не найдено» — это `raise HTTPException(status_code=404, detail="...")`, как в GET /products/{id}. Клиент обязан узнать об ошибке из статуса, а не из логов сервера.

### 500 вместо 404 / conn is not defined

- **Симптом:** `GET /products` → 500, в теле `{"detail":"Внутренняя ошибка сервера: name 'conn' is not defined"}`; путаница «как вообще появилась 500».
- **Причина:** соединение `conn` создаётся в lifespan приложения; в тестах `TestClient(app)` без контекстного менеджера lifespan не запускался, `conn` не существовало.
- **Правило:** в тестах — только `with TestClient(app) as client:`. 500 — непредвиденное исключение: смотреть traceback в терминале сервера, а не гадать по коду ответа.

### Нарушение внешнего ключа при удалении

- **Симптом:** `ОШИБКА: UPDATE или DELETE в таблице "products" нарушает ограничение внешнего ключа "order_items_product_id_fkey"` → 500; удалённый товар остаётся виден в `total`.
- **Причина:** товар нельзя удалить, пока на него ссылаются строки `order_items` (есть заказы с этим товаром).
- **Правило:** решение принимает бизнес-логика: либо `ON DELETE CASCADE`, либо проверять ссылки и отвечать 409 Conflict, либо запрещать удаление. 500 здесь — неправильный ответ: ошибка предвиденная.

### rowcount проверяется через == 0, а не is None

- **Симптом:** вопрос «почему в delete мы делаем запрос ==0, а не is none».
- **Причина:** `DELETE` возвращает **число** удалённых строк (`rowcount`), а не объект; `is None` с числом всегда False.
- **Правило:** `is None` — для объектов/значений, которых «нет»; `== 0` — для счётчиков. Проверять тип того, что реально возвращает функция БД.
